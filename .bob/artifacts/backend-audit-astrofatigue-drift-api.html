Backend Audit — AstroFatigue Drift API

Point-in-time audit of /backend (7 modules + db/). No files modified. Generated for pre-implementation review.

1. What Each File Does

File Nature Role
drift.py Deterministic Core fatigue formula. Accepts four raw signals (PVT lapses, sleep hours, circadian phase shift, task load), weights them via DriftWeights, and emits a 0–1 composite drift_score plus a 4-level risk_level. Models are grounded in Borbely two-process sleep homeostasis and SAFTE/FAST. No AI, no DB, no side effects.
simulator.py Deterministic Synthetic mission data generator. Produces a time-series of MissionDayRecord objects for one astronaut, simulating sleep degradation, PVT lapse accumulation, circadian drift, and task spikes. Seeded per astronaut so the same run always produces identical data. Used both for initial DB seeding and for What-If re-simulation.
projection.py Deterministic Two features: (1) Mission Risk Map — rolls individual per-astronaut drift trajectories into a whole-crew, day-by-day worst-case risk view; (2) What-If Simulator — re-runs one astronaut's mission with a modified task-load schedule and returns a before/after drift comparison.
replay.py Deterministic Historical Replay timeline. Flattens stored mission records into a scrubbable per-day view (TimelinePoint). Optionally extends it with project_forward(), a simple OLS linear extrapolation of the last 3 recorded days — explicitly not a model, just a trend arrow.
dependency_graph.py Deterministic Task DAG logic. Builds a DependencyGraph from task records + edge pairs, annotates each task node with its assigned astronaut's current risk_level, runs a BFS to find all downstream tasks that would slip if a given task slips, and ranks at-risk tasks by downstream impact count.
bob.py AI (watsonx) The only LLM touchpoint. Receives already-computed DriftResult sub-scores and asks IBM Granite to produce two plain-language outputs: a calm astronaut-facing message and a technical flight-surgeon brief. Falls back to a deterministic template when WATSONX_API_KEY/WATSONX_PROJECT_ID are absent. Results are cached in the DB so the same alert is never re-explained twice.
main.py Orchestrator FastAPI application. Wires all modules together via 10 HTTP routes. Handles auto-seeding on first run, self-healing of missing task tables, CORS, and global CURRENT_WEIGHTS state. All request-handling is synchronous.
db/session.py Infrastructure SQLAlchemy engine + session factory. SQLite default, swappable via DATABASE_URL env var. Provides both a context-manager version and a FastAPI Depends version.
db/models.py Infrastructure Six ORM tables: Astronaut, MissionDay, DriftScore, Explanation, Task, TaskDependency. Dialect-neutral, no SQLite-specific types.
db/repository.py Infrastructure All DB reads and writes. Reconstructs MissionDayRecord / DriftResult dataclasses from ORM rows so the rest of the app is DB-agnostic. Also builds the DependencyGraph with live risk annotation by joining MissionDay → DriftScore.
db/seed.py Infrastructure Populates the database with a 3-astronaut, 6-day synthetic mission plus an 18-task, 12-edge ISS-style DAG. Reuses simulator.py; no separate fake-data generator. Supports wipe-and-reseed or keep-existing modes, and trims task/edge lists to whatever num_days was requested.

2. Full Data Flow

1
Synthetic Mission Data — simulator.py Per astronaut, per day: hours_slept (Gaussian around a declining base), pvt_lapses (baseline + sleep-debt-driven accumulation), minutes_phase_shift (uniform increment minus re-entrainment if good sleep), task_load (from DEFAULT_TASK_SCHEDULE = [8,9,14,15,9,8]). Seeded per astronaut_id for reproducibility.
2
Fatigue Drift Score — drift.py → compute_drift_score() Four normalised sub-scores (0–1 each) are computed from the raw signals, then weighted-summed into a composite drift_score ∈ [0,1]. Default weights: RT=0.40, sleep=0.30, circadian=0.15, workload=0.15. Thresholds: <0.35=nominal, <0.55=elevated, <0.75=high, ≥0.75=critical.
3
Persistence — db/seed.py + db/repository.py Simulator output is written to mission_days + drift_scores tables. The 18-task DAG is written to tasks + task_dependencies.
4
Mission Risk — projection.py:project_mission_risk() Reads all crew records from DB via load_mission_records(). For each day, picks the astronaut with the highest drift_score as the overall risk driver. Outputs a DayRiskSnapshot list. ⚠ Risk is purely fatigue-based at this stage — task criticality and dependency position are not factored in.
5
What-If Intervention — projection.py:simulate_intervention() Accepts an astronaut_id, a day, and a task_load_delta. Re-runs simulate_mission() with a modified task schedule for that day and compares the new trajectory to stored original values. ⚠ Does not verify whether the receiving astronaut (reassign_to) has capacity — it is stored as a label only.
6
Dependency Graph — dependency_graph.py + db/repository.py:load_task_graph() Reads tasks and edges from DB. Joins DriftScore.risk_level per (astronaut, day) to annotate each task node. BFS from any task yields downstream tasks. at_risk_tasks() identifies tasks where the assigned astronaut is high/critical, ranked by downstream count. ⚠ Graph outputs are purely informational — they do not feed back into the mission risk score or the What-If calculator.
7
AI Explanation — bob.py:explain_drift() Called only when drift_score ≥ 0.55 (EXPLANATION_TRIGGER_THRESHOLD) and only from GET /explain/{astronaut_id}/{day}. Sends already-computed sub-scores to IBM Granite-13B-Instruct-v2 via synchronous httpx. Falls back to a deterministic template if credentials are absent or the call fails. Result cached in explanations table.
8
Frontend API Response — main.py Routes serialize dataclass __dict__ or hand-constructed dicts into JSON. No schema validation on output (no Pydantic response models). Errors return HTTP 404 for unknown entities; no rate limiting, no auth.

3. Bugs, Inconsistencies, Dead Code & Weak Logic

LocationCategoryFinding
bob.py line 151 Silent failure except Exception: pass (effectively) swallows every error — network timeout, bad JSON from the model, key error — with zero logging. There is no way to know from the API response whether watsonx was actually called and failed, or was never attempted. The source field says "fallback_template" in both the no-credentials case and the crash case.
projection.py:simulate_intervention() Logic bug The task schedule used for re-simulation is sliced from DEFAULT_TASK_SCHEDULE (a hardcoded 6-element list), not from the stored data. If the mission was seeded with a custom schedule or a non-6-day length, the "original" schedule used for the What-If diverges from reality on every day — meaning even days before the intervention day will show spurious deltas. The test at line 109 of test-api.py catches this for seeds, but not for custom schedules.
projection.py:simulate_intervention() Feasibility gap reassign_to is accepted and echoed back but never validated or used in any computation. The function does not look up the receiving astronaut's workload, their current fatigue score, or whether they are on a different shift that day. A reassignment to a critically fatigued crew member is silently accepted and shown as a valid intervention.
replay.py:project_forward() line 118 Wrong phase label Projected points beyond the last mission day are unconditionally labelled phase="in_mission". If projection extends past mission end they should be "post_mission", or at minimum a distinct label like "projected" so the frontend can style them differently.
main.py line 48 Global mutable state CURRENT_WEIGHTS is a module-level global modified by POST /mission/reset and then read back by POST /whatif/reassign. Under concurrent requests (Uvicorn workers > 1, or multiple async tasks) these two requests could race. Under a single-worker dev setup this is benign, but it's a hidden assumption.
main.py:whatif_reassign() Missing guard If req.day is outside the range of stored records (e.g. day=0 or day=99), simulate_intervention() clips to the schedule boundary silently. The API does not return an error — it returns a comparison where day_modified does not correspond to any actual change. The day field has no validation in TaskReassignRequest.
drift.py:workload_score() line 127 Asymmetric scoring Score is clip(ratio - 1.0), so below-average workload always returns 0.0 — rest days are scored identically to average-workload days. This means a crew member with zero task load looks the same as one at their average load. A small negative contribution (recovery credit) for well-rested, low-workload days would better reflect the two-process model.
simulator.py line 107 Weak re-entrainment model Re-entrainment is a binary step: if hours_slept >= 7.5, subtract exactly 40 minutes of phase shift; otherwise subtract 0. Real circadian re-entrainment is continuous and dose-dependent on light exposure. This produces an unrealistically sharp threshold in the data and can cause phase shift to oscillate rather than accumulate realistically.
dependency_graph.py:downstream_task_ids() O(n) frontier pop The BFS uses frontier.pop(0) on a plain Python list, which is O(n) per call. For the current 18-node demo graph this is irrelevant, but using a collections.deque would be correct BFS practice and avoids a latent performance issue if the graph grows.
bob.py Sync HTTP in async app The watsonx call uses synchronous httpx (blocking I/O) inside a FastAPI route, which is itself async-compatible. This blocks the event loop for up to 30 seconds on a slow API call, preventing any other requests from being served during that window. Should use httpx.AsyncClient or run_in_executor.
main.py line 79 Open CORS allow_origins=["*"] is fine for development but the comment says "tighten before demo-day if needed." In a hackathon context with a public URL this is a risk worth tracking.
db/repository.py line 53 Incomplete persistence updated_sleep_debt_hours is hardcoded to 0.0 on DB reads because the value is not persisted. This means if any module reads a record from DB and tries to carry the debt forward, it would start from 0 instead of the correct accumulated value. Currently no such downstream use exists, but it's a silent data loss that could become a bug if that field is ever reused.

4. Specific Evaluation

Is mission risk based only on fatigue, or does it consider task criticality / dependencies?

Fatigue only. project_mission_risk() in projection.py uses the max drift_score across crew as the day's risk. Task criticality (e.g. EVA vs log entry), task load weight in the DAG, and dependency-chain depth are not factored in. The dependency graph is computed in a parallel branch (/tasks/* routes) and never injected into the mission risk score. A crew member with a high drift score on a trivial task generates the same mission-level risk as the same score on the critical-path EVA.

Does the What-If simulator verify whether a reassignment is actually feasible?

No. simulate_intervention() in projection.py accepts reassign_to as a string label and echoes it back in the response, but performs zero lookups against the receiving astronaut's fatigue state, workload, or schedule. Any string — including a non-existent astronaut ID, a critically fatigued crew member, or the same astronaut as source — is accepted without error or warning.

Does the dependency graph affect the risk calculation or is it only visual?

Visualisation only. The graph annotates nodes with the astronaut's risk level for context, and at_risk_tasks() ranks tasks by downstream impact, but neither of these outputs flows back into project_mission_risk(), simulate_intervention(), or any score calculation. It is read-only enrichment for display, not a causal input to the risk model.

When exactly is IBM/watsonx called?

Exactly one trigger condition, in exactly one code path:

  • Route: GET /explain/{astronaut_id}/{day}
  • Condition: drift_score ≥ 0.55 (the EXPLANATION_TRIGGER_THRESHOLD constant in drift.py)
  • Cache check: only if no row exists in the explanations table for that (astronaut, day) pair
  • Credentials check: only if both WATSONX_API_KEY and WATSONX_PROJECT_ID env vars are set

Two HTTP calls are made per un-cached explanation: (1) IAM token exchange at iam.cloud.ibm.com, (2) inference call to /ml/v1/text/generation. Both are synchronous and blocking.

5. Top 5 Improvements

Ranked by combined impact across technical execution, innovation, feasibility, and real-world relevance.

#1 Integrate dependency-graph position into the mission risk score

What: Multiply each astronaut's drift score by a task criticality multiplier before computing the daily max. The multiplier could be as simple as 1 + k × downstream_count (a crew member at 0.55 drift on the EVA critical path is more dangerous than one at 0.60 drift on a log entry).

Why it matters: Currently the dependency graph is pure display. Connecting it causally makes the system do something no existing ISS tool does: rank fatigue risk by mission consequence, not just physiological signal. This is the single biggest jump in real-world impact and innovation score.

Feasibility: The data is all present. load_task_graph() already has downstream counts; project_mission_risk() already iterates per-astronaut per-day. Plumbing the graph into the risk rollup is 20–30 lines of code with no new dependencies.

#2 Add feasibility checking to the What-If Simulator

What: Before accepting a reassignment, look up the receiving astronaut's current drift score and workload for that day. Reject or warn if: (a) the receiver is already high/critical risk, (b) adding the delta would push their load over 2× their rolling average, or (c) they have a dependency-critical task on that same day.

Why it matters: The simulator currently lets you "solve" a fatigue problem by reassigning to someone who is worse off. That is a demo-breaking flaw if a judge tries it. Real operational tools (e.g. NASA's EAST system) gate reassignment on crew availability checks.

Feasibility: All required data is in the DB. Needs a secondary load_mission_records call for reassign_to and 15–20 lines of logic in simulate_intervention(). Return a structured feasibility block in the API response alongside the trajectory comparison.

#3 Switch Bob to async HTTP and add structured error telemetry

What: Replace synchronous httpx.post() in bob.py with httpx.AsyncClient (or move the call to run_in_executor). Log the exception type and whether fallback was used in the API response ("source": "fallback_template:network_error" vs "fallback_template:no_credentials").

Why it matters: A 30-second blocking IAM + inference call currently stalls the entire server for all concurrent requests. On demo day with multiple judges hitting the UI simultaneously, this will produce visible latency or timeouts. The telemetry fix makes the AI-vs-fallback distinction transparent, which is important for credibility.

Feasibility: Two-line change for async; four-line change for error telemetry. No architectural risk.

#4 Persist and carry forward sleep debt across DB reads

What: Add a sleep_debt_hours column to the drift_scores table (the updated_sleep_debt_hours field already exists in DriftResult but is not written). Restore it on read so project_forward() and any future re-simulation from mid-mission can carry the correct accumulated debt rather than starting from 0.

Why it matters: If the system is ever extended to ingest real sensor data mid-mission and re-run the formula from the last stored day, starting with 0 sleep debt will produce incorrect scores. This is a latent correctness bug in the persistence layer that becomes critical the moment the app moves beyond pure retrospective demo data.

Feasibility: One schema migration + three-line write in seed.py + one-line read in repository.py. Entirely additive.

#5 Expose a multi-astronaut What-If endpoint with crew-level re-balance

What: Add a POST /whatif/crew-rebalance route that accepts a day and automatically finds the best reassignment across the whole crew: for the highest-risk astronaut on that day, enumerate their tasks, and for each task score every other crew member's feasibility (drift headroom + workload capacity + no dependency conflict), picking the optimal swap. Return both the per-astronaut before/after and the updated mission-level risk snapshot.

Why it matters: The current /whatif/reassign is single-astronaut and manual. An automated crew-level optimizer is the "what would NASA's scheduling AI actually do?" answer — a meaningful jump in innovation score and in the story told on demo day. It also showcases the dependency graph as a constraint, not just a display layer.

Feasibility: Can be built entirely on existing primitives — simulate_intervention(), project_mission_risk(), and the task graph. No new data, no new dependencies. The algorithm is a greedy search over a small space (3 astronauts × <18 tasks) so runtime is negligible.
